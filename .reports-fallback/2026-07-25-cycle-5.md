tail of the previous sentence. The existing comment already says this; I

## 1. A dropped tunnel looked exactly like a quiet Claude — `9eeccc3`

This is the failure mode FOCUS.md's *current top priority* names by name
("watch specifically for tunnel drops"), and it turned out to be invisible by
construction on both sides.

**potato's side.** `crt-secretary.py`'s `send_to_claude()` threw away its
result. On the remote path, `_bridge_request()` returns `""` for *any* socket
failure — tunnel down, bridge stopped, connection refused. So the send was a
silent no-op, and `handle()` went on to:

1. fire the `thinking` earcon — a promise to the user that an answer is coming,
2. sit through `wait_for_claude_reply()`, polling a socket that would never
   answer, until `CLAUDE_IDLE_SECS` expired,
3. and finish with `route_claude_reply("")` → *"I sent that to Claude but
   didn't catch a reply — check the screen."*

Nothing was sent. And the screen it points at is blank **precisely because**
the brain isn't there. A user following that instruction learns nothing, and
the actual cause — a dead reverse tunnel — is recorded nowhere at all.

**mandark's side was equally blind.** `crt-remote-claude-bridge.py`'s `SEND`
handler ran two `tmux send-keys` calls, ignored both return codes, and replied
`OK` regardless. A tmux session that had died or been renamed answered exactly
like a working one. It now checks both and replies `ERR <tmux's own reason>`.
The Enter is checked *separately* on purpose: the literal text can land and the
newline not, which leaves a half-typed prompt sitting in Claude's input and no
reply — the most confusing of the failure modes, and completely silent before.

**Safe in either deployment order**, which matters because the two halves live
on different machines and I can only deploy one of them:

| | old secretary | new secretary |
|---|---|---|
| **old bridge** | today's behaviour | detects the tunnel-down case (`""`); still trusts a stale `OK` |
| **new bridge** | ignores the response, unchanged | full detection |

`OK` is byte-identical for the working case, so nothing has to be restarted in
lockstep. The dominant failure — the tunnel itself dropping — is caught by the
potato half alone.

**What the console does now when an utterance doesn't land:** the `oops`
earcon, a spoken line deliberately worded to be distinguishable *by ear* from
the reached-Claude one ("I can't reach my brain right now, so that didn't go
anywhere"), the same line pushed to the `mono` window `handle()` just switched
to so the tube isn't blank, and an append to `~/.crt/brain-unreachable.log`
with the reason. `bin/crt-wake-router.py`'s `none` route already specified this
behaviour — *"the caller should give a short honest earcon/line … NOT
silence"* — it simply had no caller on this path until now.

**A quieter bug fell out of the same fix.** `_confirm_in_background()` —
STT-CONFIDENCE.md's background confirmation pass — recorded a Claude call and
then scored the resulting empty reply as a *mismatch*. So every utterance
spoken while the tunnel was down taught the confidence model that its own local
playbook disagreed with Claude, from an exchange that never happened. It now
returns before recording anything.

18 new tests. The ones that matter assert behaviour, not wording: `handle()`
must not wait on a send that never landed (the stub `fail()`s if it's called),
must not fire `thinking`, must not claim it sent anything, and must still fire
`thinking` on the success path.

## 2. A status command that could answer about the wrong port — `26cd8df`

`bin/crt-mandark.sh` is the tool Zach runs to answer "is the brain reachable".
Its `probe_bridge()` always read `$PORT` — `CRT_MANDARK_PORT`'s default, 8993 —
while `current_port()` directly below it read the port persisted in
`~/.crt/mandark.conf`. So `CRT_MANDARK_PORT=9001 crt-mandark.sh on` followed by
a plain `crt-mandark.sh status` printed:

```
config: ON  (port 9001)
bridge reachable now: no
```

…having probed 8993. Two lines of a three-line diagnostic disagreeing about
which port the console uses, with no indication. Same class as the silent-earcon
bug: a tool that gives confident answers about something other than what you
asked.

`probe_bridge()` now takes the port as an argument, every caller passes the
effective one, and both reachability lines name the port they probed. With the
config OFF there is no port in use, so it still probes the default — that
genuinely answers "is the bridge up if I turn this back on" — but the line now
says that's what it did.

The test stands a real listener on 19001 and leaves 8993 empty, so
`reachable: yes` is only achievable through the configured port. **I confirmed
it fails against the pre-fix script**, not just passes after — my first draft of
this test was fake-green (it grepped the whole output for "port 19001", which
also appears in the *config* line, so it passed either way). Both assertions
were rewritten.

## New issues found

- **Two subsystems, same shape: a success path that never checked whether it
  succeeded.** `send_to_claude()` discarded its result; the bridge's `SEND`
  handler discarded two return codes. Both then reported success. This is the
  same class as the `[ -f ]` guard from cycle four and the silent-earcon bug
  before it, and it's worth naming as the project's signature defect: *the
  code that reports the outcome is not the code that observed it.*
- **A stale instruction can be a no-op as easily as stale code.** FOCUS.md's
  "FIRST STEP EVERY CYCLE (2026-07-21): pull from crt-vm before doing anything
  else" requires `bin/crt-sync-vm.sh`, which no longer exists — along with
  `bin/crt-vm-*`, `bin/dexter-*` and `systemd/crt-vm-*`, all retired with the
  potato move. It reads as a live gate and does nothing. Registered for
  FOCUS.md in `BATCH-NOTES.md`.
- **Ranked-backlog item 1 is mostly already done, including its "real bug".**
  Checked each claim: the dead dexter/crt-vm files are gone; `grep -rn 8992`
  over the whole repo returns nothing; and the *"port 8993 collides — both
  `crt-remote-claude-bridge.py` and `crt-scanner-feed.py:32` claim it"* bug is
  resolved because `crt-scanner-feed.py` no longer exists (`crt-console.sh`
  lines 201-204 record the removal, for exactly this collision). Only the
  config-consolidation half is live.
- **The consolidation that remains is a design question, not a chore.** 8993 is
  typed into six files under **three different env var names** —
  `CRT_MANDARK_PORT`, `CRT_CLAUDE_REMOTE_PORT`, `CRT_REMOTE_BRIDGE_PORT` — and
  8991 into five. The three names aren't redundant; they're genuinely different
  roles (listen / dial / probe-default). Picking a canonical one needs a
  decision, and a config module that half the boot path doesn't read would be
  worse than the current sprawl. Flagged rather than done.
- **The new `oops` earcon does not open a duck hole.** Checked before adding it:
  `crt-secretary.py`'s `play_earcon()` calls `crt-earcon.sh` with no
  `--device`, which lands in the `*)` branch → `default` → and `9063661`
  already made an unknown device duck. Confirming rather than assuming, because
  this is exactly where this project's bugs live.
