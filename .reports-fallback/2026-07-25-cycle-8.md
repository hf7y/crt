## 1. "Spoken" did not mean audible — `3244250`

`play_wav()` ran `subprocess.run(["aplay", ...])` and returned `True` on the
next line. The exit status was never read, so a device that does not exist, is
busy, or is misnamed produced a confident success from a silent room.
`crt-secretary.py`'s `speak()` then dropped crt-tts.py's exit status too — its
`sh()` helper captures stdout and stderr, and nothing ever looked at either.

Every audio bug this project has had was a wrong device name: `plughw:0,0`
with no capture stream, the dead dexter earcon URL, the `:8992` default. The
output path was the one where that class could not be noticed at all.

`play_wav()` now returns False and names the device plus aplay's own last line
of stderr. `speak()` checks it and **puts the words on the tube** via
`crt-think.sh` — a reply that cannot be heard is not thereby a reply that has
to be lost. The failure report deliberately does not try to speak itself.

**15 tests, injected at PATH** with a real executable named `aplay` that
really exits with the status under test, plus an end-to-end run of crt-tts.py's
real CLI against a fake synthesizer. **10 fail against the parent.**

Two things worth naming from writing them:

- The first run of that file **passed for the wrong reason.** The fake
  crt-tts.py was a `/bin/sh` stub, and `speak()` invokes it as
  `python3 crt-tts.py` — so it exited nonzero with a SyntaxError and every
  failure assertion passed without reaching the code under test. Fixed, and
  the reason is a comment in the file.
- `tests/test_tts_capture_duck.py` had `subprocess.run = lambda *a, **k: None`.
  Real `subprocess.run` returns a CompletedProcess, so that stub silently
  asserted nothing downstream would ever read aplay's exit status — which is
  precisely the bug that sat in `play_wav()` the whole time that test was
  green. Replaced with the same real-aplay-on-PATH seam.

## 2. A phone that never rang, reported as a missed call — `99a8dc3`

`ring_tone_path()` ignored sox's exit status *and* its stderr, then cached the
path regardless. `mkstemp` has already created that file — so with sox missing
or failing, the cache held a real, existing, **zero-byte** wav, and
`os.path.exists()` said yes for the rest of the process's life. Every ring
after that handed aplay an empty file, and no later call could recover even
once sox worked. The ring's own aplay was `Popen(stderr=DEVNULL)` with its
exit status never read.

What that produced on screen: `[ring] ringing (4)`, four silent cycles,
`[ring] no answer`. Two opposite facts — one about you, one about this machine
— reported as the same one. Same class as `crt-mandark.sh` probing the wrong
port (`26cd8df`) and `transcribe_remote()`'s `""` (`ba33791`).

`crt-earcon.sh` checks for sox by name and exits 1 with a message. This path —
the one whose entire job is to summon someone to the handset — checked
nothing.

Now: an unplayable tone is never cached, a ring that cannot be produced never
enters the state machine, and a burst that dies on its own aborts the ring
within ~100ms with `! phone never rang` on the tube and a pane line that says
the fault is here. **16 tests with real sox/aplay on PATH; 14 fail at the
parent.**

One behaviour change worth flagging as an improvement rather than a fix: with
no sox installed at all, the old code raised `FileNotFoundError` out of the
capture loop, so a `ring` line in the CTL file **killed the sole mic reader**.
It now reports and carries on.

## 3. The tool that stands in for your ear could not say "I measured nothing" — `f187a45`

This is the one I'd want you to read twice, because it touches a finding
already in FOCUS.md.

`bin/crt-earcon-loopback-test.py` is what the `nightly-batch` skill allows
instead of your own ear, and stability-bar item 2 is waiting on a re-run of
it. It had two verdicts where the situation has three:

| what happened | old output | what it means |
|---|---|---|
| played, mic heard it | DETECTED | fine |
| played, mic did not hear it | not detected | indicts the USB adapter |
| **never played at all** | **not detected** | indicts a device name |

sox's and aplay's exit statuses both went to `/dev/null` — a strange thing for
*this* tool to have done, since its own header says it exists because an exit
code is not evidence a sound was made. It swung so far that it read no exit
codes at all, and so could not tell the bottom two rows apart.

FOCUS.md's 2026-07-23 handset result — 0.1x above baseline, read as "this USB
adapter cannot play and record simultaneously" — rests on exactly that
distinction, and the capture-duck work of cycles 3, 4 and `fe46ac1` rests on
that reading. **I am not claiming it is wrong.** 0.1x is also just what a
working-but-deafened adapter looks like, and the TV path registered 5.0x in
the same session, which argues aplay was working at least there. What I am
saying is that the tool could not have established it, and now it can. One
command settles it (§4).

Two more of the same family, fixed alongside: a **failed baseline recording**
returned rms 0.0, and detection is `best / (base_rms + 1e-6)` — so a broken
mic made *every* device come back DETECTED. And `main()` exited 0 whatever it
found; it is now 0 detected / 1 not detected / 3 inconclusive, which is
ranked-backlog item 6's actual ask (pass/fail plus numbers, not a number a
person has to read).

**14 tests** over the pure verdict and exit-code seams. Honest caveat: they
*error* rather than fail against the parent, because the old code had no seam
at which the three-way distinction could be expressed — which was the defect.

## 4. Stress-test of what I touched

Checked against this project's real failure modes, not against the suite being
green:

- **A failing playback must not leave capture muted.** A dead speaker becoming
  a dead microphone would be a strictly worse bug than the one being fixed.
  The duck is decided once before playback and released in `finally`; pinned
  by a test asserting `mute 1`/`mute 0` still balance when aplay exits 1.
- **`speak()` now returns a bool where it returned `None`.** Checked every
  playbook handler: all return their spoken text explicitly, none return
  `speak(...)`, so `confidence_route`'s `local_answer` cannot become `True`.
  Empty text is treated as nothing-to-say, not as a fault, so it does not
  report a failure for an utterance nobody meant to make.
- **The ring's failure check must not block the capture loop.** `poll()`,
  never `wait()`; a burst still playing reports nothing. Tested.
- **An answered ring must not read as a failed one.** Terminating aplay gives
  a negative exit code, which `failure()` treats as success — otherwise every
  answered call would become an error. Tested.
- **Sole-reader constraint:** untouched. Still one `arecord`, one reader.
- **Control-file race:** untouched; none of tonight's paths read CTL state.
- **Pre-existing, not fixed, now that I have looked at it:** the first `ring`
  runs sox synchronously *inside* the capture loop, which is cycle seven's
  "capture is blind while whisper runs" in miniature. It was already like
  that, sox synth is fast, and the widened pipe (~8.2s) covers it — but it is
  a real instance of the pattern and worth someone's attention before the ring
  gets used for anything longer.

## 6. New issues found this cycle

- **The same defect four times in one night suggests it is structural, not
  four mistakes.** Every one is "start a subprocess that makes noise, never
  look at what happened to it" — and the reason is that the *sound* is the
  return value, so nobody thinks of the exit code as carrying information.
  Cycles 5–7 found the identical shape in `send_to_claude()`,
  `capture_pane()`, and `transcribe_remote()`. The output half of the console
  had simply never been swept for it.
- **The loopback tool is the instance that matters most**, because it is the
  one whose output gets promoted into FOCUS.md as evidence. A measuring
  instrument that cannot report its own failure launders a broken setup into
  a hardware conclusion.
- **`last_line()` now exists twice**, in `crt-stt-solo.py` and
  `crt-earcon-loopback-test.py`, because scripts in `bin/` have hyphens in
  their names and cannot import each other. Small, but it is the same forced
  duplication that drives ranked-backlog item 1's config sprawl, and it will
  keep happening until there is one importable module. Registered as a
  question rather than solved.
