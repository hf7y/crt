## 1. Bar item 2 (handset play-while-capture): the ref-count fix had a worse failure mode than the bug it fixed — `49eec0d`

Last night's `0343f21` made the CTL-file capture mute reference-counted so two
overlapping ducks compose. Correct as far as it goes, but it silently removed
the old flag's accidental self-healing: with last-write-wins, **any** later
`mute 0` restored capture, so a duck whose producer died mid-playback got
cleaned up by the next sound that played. With a counter, that leaked
increment never comes back down — `crt-stt-solo.py` goes permanently deaf, no
error, no crash, indistinguishable from the mic dying.

Three things fixed:

1. **Momentary control lines are no longer replayed at startup.** `main()`
   reads the append-only CTL file from byte 0 on every start (deliberate — a
   knob-tuned `vad`/`trail` level survives a restart). So *one* leaked
   `mute 1` anywhere in that history muted capture on every subsequent boot,
   forever, since the file is never truncated. The same replay also re-fired
   any stale `ring 4` — the phone rang at boot. `mute`/`ring` now apply only
   when they arrive live.
2. **`CRT_CTL_MUTE_MAX_SECS` (default 45s, 0 disables).** A held mute is
   force-cleared with a loud `WARNING` once it outlasts any plausible handset
   duck. Backstop for what no handler can catch (SIGKILL, power loss).
   Unmuting is the safe direction here: clearing early only risks VAD hearing
   our own playback, which this adapter can barely record anyway — that 0.1x
   measurement is the whole reason the duck exists.
3. **`crt-tts.py` installs a SIGTERM handler** so `play_wav()`'s `finally:`
   runs. Measured directly tonight: bash runs its EXIT trap on SIGTERM (so
   `crt-earcon.sh` was already fine), but **Python skips `finally:` entirely**
   — so `tmux kill-window` or a supervisor restart on a mid-playback
   `crt-tts.py` leaked its duck every time. That's the common case, now closed
   cleanly rather than waiting out the watchdog.

Witness: `tests/test_capture_duck_signal_safety.sh` drives the real CLI (fake
`espeak-ng` + a blocking fake `aplay`), kills it mid-playback, and asserts the
CTL file's net mute balance returns to 0. Confirmed it fails without fix 3
(`CTL: mute 1/`, unbalanced). Plus 11 new cases in `test_stt_solo_helpers.py`.

## 2. Bar item 3 (capture device by name): the silent half of the original bug was never fixed — `db39b61`

The 2026-07-23 07:10 finding has two halves. Resolving the device by name
(`3b87b14`) fixed the *cause* of that night's dead capture. The note's actual
complaint — *"the process restarted silently exits (no error, no capture)
rather than failing loudly"* — was still true at HEAD.

Reproduced against the committed version with a fake `arecord` that fails the
way a nonexistent device does: **exit 0, 118 bytes of output, not one word
about the failure.** Name resolution can't help with the next cause anyway
(USB replug mid-session, device grabbed by a second reader, an ALSA change).

- `arecord`'s stderr goes to a temp file instead of `/dev/null` (a pipe could
  block on a buffer nobody drains), so its own diagnosis survives.
- On EOF from the capture stream: print `capture_death_report()` — which
  device died, whether it ever produced audio at all, how long it ran, the
  exit code, the last lines of `arecord`'s stderr, and the `CRT_AUDIO_DEV`
  escape hatch — then **exit 3**. The nonzero exit matters as much as the
  text: a dead process is visible to a supervisor and to `echo $?`; a live
  process that hears nothing forever is not. The tmux window runs
  `python3 ./crt-stt-solo.py; exec bash`, so the message stays on the pane.
- Name resolution now falls back to the **first card in the `arecord -l`
  CAPTURE listing** instead of the hardcoded `plughw:0,0`. That constant is
  exactly what broke on potato — card 0 there is playback-only and absent
  from the capture listing entirely, so the old fallback was
  guaranteed-silent-failure. It also warns on stderr when it had to guess.

Witness: `tests/test_capture_death_loud.sh` (asserts nonzero exit + every
thing the report has to name), 5 new cases in `test_capture_device.py`.

## 3. Bar item 1 (sticky wake window): solved a quarter of the live bug — `f2a40fc`

The live report it was built for: "Potato, this is Zach" woke the console,
then **four** follow-ups in the same breath were all gate-dropped.
`consume_arm_with_followup()` disarmed on the first follow-up, and
`crt-stt-solo.py` returns straight after dispatching it without re-arming — so
follow-up #1 got through and #2/#3/#4 were dropped exactly as before. The same
complaint, one utterance later.

A consumed follow-up now **slides** the window. Two guards, because "keep
listening" is the dangerous direction in this room:

- **`CRT_WAKE_ARM_MAX_SECS` (default 60s)** — a per-session ceiling set by the
  wake word and never pushed back by follow-ups. CLAUDE.md's premise is
  ambient chatter and a noisy mic; an uncapped sliding window would let room
  noise keep re-arming itself until the console is effectively always on.
  Saying the wake word again is deliberate, so it starts a fresh session.
- **A continuation window timing out no longer reports a timeout to
  `crt-wake-judge.py`.** The consumed follow-up already proved the wake was
  wanted; filing `timeout-with-leftover` when the conversation later ends
  would argue the opposite and poison `WAKE-TUNING-STATE.md`'s ground truth —
  and the judge writes real config changes off that log.

Still opt-in, still default OFF (`CRT_WAKE_ARM_ENABLED`). The original
four-in-one-breath transcript is now a regression test.
