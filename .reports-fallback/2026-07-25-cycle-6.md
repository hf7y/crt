## 1. A tunnel that drops after the send — `931c0d9`

Cycle five made an utterance that *never left* distinguishable from a quiet
Claude. The same conflation was still fully live one step later, on the same
FOCUS.md top-priority path, because `capture_pane()` collapsed failure into
`""` and `wait_for_claude_reply()` diffed against that as if it were a real,
empty pane. Two consequences, both measured against the parent commit by
injecting at the bridge socket:

**No baseline → the console reads you its own scrollback.** `handle()` takes a
`before` snapshot, sends, then diffs. If that first capture fails and the pane
reads fine afterwards, every line on it counts as new. A 200-line scrollback
came back as "the reply", so `route_claude_reply()` spoke the first 160
characters of an unrelated old exchange into the earpiece and handed the rest
to `print_full()` — which is `bin/crt-print.sh`, a **Phomemo M02 thermal
receipt printer**. Measured at the parent commit: 200 lines printed, spoken
text beginning `scrollback line 0: …`.

**A drop after the send → the wrong sentence again.** Once the tunnel is gone,
every later capture is `""`, the diff comes out empty, and the console said
*"I sent that to Claude but didn't catch a reply — check the screen"* — the
same sentence, with the same two lies, that `9eeccc3` was about. It just
reaches it by dropping *after* the utterance instead of before it. FOCUS.md
names tunnel drops as the thing to watch for; this was the half that happens
once the utterance is already gone.

**The fix rests on one distinction:** `capture_pane()` returns `None` when the
pane could not be read and `""` only when it genuinely was. On the remote path
an empty response *is* the failure signal — `_bridge_request()` returns `""`
for a dead tunnel, and mandark's own `capture_pane()` returns `""` for a dead
tmux target — and a live Claude Code pane is never legitimately empty. So this
needed **no bridge-side change**, which matters: the mandark half of `9eeccc3`
is still undeployed, and this fix must not depend on it.

`wait_for_claude_reply()` now returns `(reply, status)`. A failed capture is no
longer mistaken for pane growth — it used to reset the stability timer *and*
fire `on_partial`, putting "…composing" on the tube on the way to reporting a
reply nobody saw. Consecutive misses are tolerated up to
`CRT_SECRETARY_CAPTURE_MISSES` (3) so a hiccup doesn't end a real wait; past
that it returns rather than spending the remaining 120s of `CLAUDE_MAX_WAIT` to
reach the same answer. **This is not a by-ear number** — it's "long enough to
ride out a hiccup, shorter than the timeout it replaces", which is decidable
from the code.

The third outcome gets the third line it needs. `REPLY_UNOBSERVED_LINE`
deliberately does *not* say "check the screen": whether the answer is on the
tube is exactly what this outcome doesn't know. `SECRETARY.md` gained the
three-outcomes table and the rule behind it — **the console may only report
what it observed.**

Two smaller things fell out:

- The log verdict now distinguishes them. `NOT DELIVERED (sent, but the pane
  went unreadable)` contradicted itself — the same confidently-wrong-diagnostic
  class as `26cd8df`'s port. It reads `DELIVERED, REPLY UNOBSERVED` now, and a
  test asserts the log does *not* say `NOT DELIVERED` for this case.
- `_confirm_in_background()` gets cycle five's fix one step later: an answer
  nobody could read is not an answer that disagreed, so it no longer scores one
  against the confidence model.

14 new tests. **9 of the 14 fail against the parent commit**; the 4 that pass
in both are the deliberate unchanged-behaviour guards — a working exchange
(byte-identical), a single transient miss that still gets its answer, and
`capture_pane()`'s two success cases. They inject at the bridge socket rather
than stubbing `capture_pane()`, because stubbing it reproduces **neither** bug
— my first probe did exactly that and reported both bugs as still present after
the fix.

**Confirmed on the live path, not just in tests:** `crt-console.sh:193` pins
`CRT_CLAUDE_REMOTE_PORT=8993` and `CRT_STT_SINK=secretary` in the `stt`
window's boot line, so the remote branch this fixes is potato's default, not an
opt-in.

## New issues found this cycle

- **A report format can be a bug.** Three cycles of human feedback went to an
  already-closed question because of duplicated headings in a file. Worth
  generalising: this tier's outputs — reports, logs, spoken lines — are
  interfaces with the same failure modes as its code, and the ones that carry
  *correction* back in are the expensive ones to get wrong.
- **The signature defect held for a third subsystem, and one layer deeper than
  last time.** `capture_pane()` reported a failure as data, and every caller
  above it then reasoned confidently from it. Cycle five named the class as
  *"the code that reports the outcome is not the code that observed it"* — this
  is the version where the observation itself is unfalsifiable, because failure
  and a real value share one representation. The concrete lesson for the next
  cycle: **a function that returns `""` on error is the same defect as one that
  returns exit 0 on error**, and this repo has more of them (see below).
- **`transcribe_remote()` in `crt-stt-solo.py` is the same shape, still open.**
  FOCUS.md's own 2026-07-23 00:40 note already flags it: it returns `""` on any
  error talking to `CRT_WHISPER_SERVER`, so an unreachable whisper server is
  indistinguishable from a silent room. **Not fixed tonight** — unlike the
  secretary case, `""` there is genuinely ambiguous (whisper legitimately
  returns nothing for silence), so it needs a real decision about the fallback
  FOCUS.md wants rather than a sentinel. Registered in `BATCH-NOTES.md`.
- **My own first witness for §1 was fake-green**, and it's the second cycle in
  a row that's happened (cycle five's port test grepped the wrong line). It
  stubbed `capture_pane()` directly, so it reported both bugs as *still
  present* after the fix — the stub bypassed exactly the function the fix
  changed. The rule that catches it: **inject at the boundary the bug lives
  at**, which for anything on this path is the bridge socket.
