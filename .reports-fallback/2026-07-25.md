## 1. Your note on the mid-utterance duck — `f13c7a4`

You flagged the "Observation, deliberately not changed" bullet: the VAD checks
`MUTED` only when *starting* an utterance, so a duck arriving mid-utterance
doesn't stop buffering. Fixed.

The previous cycle's reason for leaving it — "changing when an utterance gets
truncated is a by-ear tuning call" — was reasoning about the wrong fix. There
are three possible behaviours, not two:

| | what whisper gets |
|---|---|
| buffer the ducked audio (what it did) | our own earcon/reply, transcribed as the speaker's words |
| close the utterance at the duck | truncation — and with `CRT_EARCON_ON_THRESHOLD=1` the `heard` earcon fires *at onset*, so this cuts every utterance to nothing |
| **freeze and excise (landed)** | speech either side of the duck, spliced |

Only the middle one is the by-ear call. Freezing isn't: ducked chunks are
dropped and the silence timer stops advancing while they are, so playback
neither enters the buffer nor ends the utterance. A duck outlasting
`CRT_MUTE_UTT_MAX_SECS` (new, 2s, 0 disables) closes the utterance normally,
so a long spoken reply can't hold one open.

Excising can drop real speech if you talk straight through the duck. That's
deliberate, and it leans on the measurement the duck exists for: this adapter
records its own playback at ~0.1x, so those frames are mostly playback anyway,
and a short splice is kinder to whisper than a beep sitting inside the
sentence. **The 2.0s bound is a guess** — it's the third by-ear number on the
pile with `CRT_WAKE_ARM_SECS` and `CRT_WAKE_ARM_MAX_SECS`.

Witness: `tests/test_duck_midutterance_excision.sh` drives the real CLI with a
fake capture that ducks itself mid-sentence and measures the WAV handed to
whisper. 400cs at the parent commit, 300cs here, and the truncating
alternative would be 110cs — all three outcomes are distinguishable, so the
test pins which one is in force, not just "something changed". Plus 8 cases in
`test_stt_solo_helpers.py` on the extracted pure decision function
(`utt_chunk()`).

`STT-MECHANISM.md` gained a paragraph on this, since "the console talked over
you and the word straddling that moment lost its middle" is now a real
explanation for a garbled transcription that a future instance should know
about before blaming whisper.

## 1. The SIGHUP hole — `2a346ae`

Last night's `49eec0d` gave `crt-tts.py` a SIGTERM handler so `play_wav()`'s
`finally:` releases the CTL-file capture duck, and its docstring names
`tmux kill-window` as the case it closes. **It does not close that case.**

Measured against a real tmux this cycle: a pane process receives **signal 1
(SIGHUP)**, not 15 — tmux closes the pty and the kernel hangs the process
group up. And I re-derived the underlying table rather than trusting it:

| | SIGTERM | SIGHUP | SIGINT |
|---|---|---|---|
| bash `EXIT` trap | runs | runs | runs |
| python `finally:` | **skipped** | **skipped** | runs |

So `crt-earcon.sh` was fine on all three, and `crt-tts.py` still leaked its
`mute 1` on every window teardown mid-playback — which is the leak that makes
`crt-stt-solo.py` permanently deaf through the reference count.

Both producers now run through both signals in
`test_capture_duck_signal_safety.sh`. Against the pre-fix code the new half
fails as it should (`leaked a capture duck on SIGHUP (CTL: mute 1/)`) while
the SIGTERM half passes — which is precisely how the hole survived: the test
was written alongside the fix and agreed with it.

## 2. `crt-stt-solo.py` had no handler at all — `fe9bc1a`

Same audit applied to the process that matters most. It now traps both
signals, reaps the capture child, prints `[crt-stt] stopped; released <dev>`,
and exits 0 instead of being killed mid-loop with status 128+signum that a
supervisor reads as a crash.

**A suspected bug that is not real, recorded so it isn't re-derived.** I
expected a leftover `arecord` holding the USB capture device — serious now
that capture death exits 3 (`db39b61`), since the restart would be blocked by
the corpse of the previous run. It does not happen: when the process exits,
the read end of `arecord`'s stdout pipe closes and `arecord` dies of SIGPIPE
on its next write, handler or not — gone within ~3s in both versions. My first
probe *appeared* to show an orphan because it was signalling `setsid`'s
already-exited pid instead of python's, so nothing had been killed at all.
`reap_capture()` is therefore determinism, not a repair, and its docstring
says so.

The real gain is narrower but genuine: "stopped on purpose" and "went silently
deaf" were indistinguishable from both the pane and the exit code.

The test labels its own assertions by strength — mic-release and
no-false-`CAPTURE DIED` are regression guards that passed before the change;
the announcement and exit-0 checks are real witnesses that fail against it.

## 3. A defect I introduced, caught by stress-testing — `3d5ef8f`

The farewell print in `fe9bc1a` was tested against a process whose stdout was
a plain file — the `systemctl stop`/`pkill` shape. The tmux shape differs in a
way that matters: tmux sends SIGHUP *because* it destroyed the pty, so writes
to stdout fail with EIO by the time the handler runs. The unguarded print
raised at the end of an otherwise perfect shutdown and exited 1 —
reintroducing the exact "clean stop looks like a crash" reading it was added
to remove. Measured with a closed pty master: HEAD exits 1, guarded exits 0.
That scenario is now the last case in the test.

**Class worth knowing:** cleanup code that writes to a tty that is already
gone. It applies to any farewell/diagnostic output in a tmux-hosted process
here — including the `CAPTURE DIED` report's own stderr path, which I did not
change (a torn-down pane takes the deliberate-stop path instead, so it is not
currently reachable, but it is the same shape).

## 1. Bar item 2 (handset play-while-capture): the ref-count fix had a worse failure mode than the bug it fixed — `49eec0d`

Last night's `0343f21` made the CTL-file capture mute reference-counted so two
overlapping ducks compose. Correct as far as it goes, but it silently removed
the old flag's accidental self-healing: with last-write-wins, **any** later
`mute 0` restored capture, so a duck whose producer died mid-playback got
cleaned up by the next sound that played. With a counter, that leaked
increment never comes back down — `crt-stt-solo.py` goes permanently deaf, no
error, no crash, indistinguishable from the mic dying.

Three things fixed:

1. **Momentary control lines are no longer replayed at startup.** `main()`
   reads the append-only CTL file from byte 0 on every start (deliberate — a
   knob-tuned `vad`/`trail` level survives a restart). So *one* leaked
   `mute 1` anywhere in that history muted capture on every subsequent boot,
   forever, since the file is never truncated. The same replay also re-fired
   any stale `ring 4` — the phone rang at boot. `mute`/`ring` now apply only
   when they arrive live.
2. **`CRT_CTL_MUTE_MAX_SECS` (default 45s, 0 disables).** A held mute is
   force-cleared with a loud `WARNING` once it outlasts any plausible handset
   duck. Backstop for what no handler can catch (SIGKILL, power loss).
   Unmuting is the safe direction here: clearing early only risks VAD hearing
   our own playback, which this adapter can barely record anyway — that 0.1x
   measurement is the whole reason the duck exists.
3. **`crt-tts.py` installs a SIGTERM handler** so `play_wav()`'s `finally:`
   runs. Measured directly tonight: bash runs its EXIT trap on SIGTERM (so
   `crt-earcon.sh` was already fine), but **Python skips `finally:` entirely**
   — so `tmux kill-window` or a supervisor restart on a mid-playback
   `crt-tts.py` leaked its duck every time. That's the common case, now closed
   cleanly rather than waiting out the watchdog.

Witness: `tests/test_capture_duck_signal_safety.sh` drives the real CLI (fake
`espeak-ng` + a blocking fake `aplay`), kills it mid-playback, and asserts the
CTL file's net mute balance returns to 0. Confirmed it fails without fix 3

## 2. Bar item 3 (capture device by name): the silent half of the original bug was never fixed — `db39b61`
