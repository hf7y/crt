## 1. A dead recogniser is not a quiet room — `ba33791`

`transcribe_remote()` returned `""` on any error talking to
`CRT_WHISPER_SERVER`: unreachable host, timeout, HTTP 500, unparseable body.
`""` is also what the server returns when it genuinely heard nothing. One
value, two meanings, and `emit()` drops both on the floor without a word.

This is the last open instance of the defect class the last two cycles closed
elsewhere — `send_to_claude()` in `9eeccc3`, `capture_pane()` in `931c0d9` —
and it was carried in `BATCH-NOTES.md` as needing a decision. It turned out to
be two questions wearing one coat:

- **Should failure be distinguishable from silence?** Not a decision. It is
  decidable from the code, and the answer is yes.
- **What should the console DO about a dead server?** That one is yours, and
  it is still open (§6).

Only the first is done here. `transcribe_remote()` returns `None` when it
could not get an answer out of the server at all, and `""` only when the
server really did transcribe the clip as nothing. `transcribe()` no longer
launders that back into `""` on the way up — and a local `whisper-cli` that
exits nonzero counts as a failed recognition too, not a quiet room (missing
model file, unreadable WAV, OOM on the Pi).

**What you'd actually see**, which is the point of the change: `! stt lost it`
flashes on the tube every single time it happens — you're looking at the tube,
not at the `stt` pane's scrollback — and the pane carries one
`TRANSCRIPTION FAILED (N in a row) … This is NOT a silent room.` line on the
first failure and every tenth after it, so an hour-long mandark outage leaves
a readable trail without burying the pane. Plus a line when it starts working
again, so the pane never ends on a failure that has since stopped being true.
Both are pure string builders, same posture as `capture_death_report()`, and
the pane write is guarded the same way the exit message is — a message about a
failure must not become a second failure on a pty tmux already took away.

**26 tests, injected at the socket**: a real `http.server` on a real port, and
a bound-then-closed port for the unreachable case. Not a urllib stub — cycle
six learned twice that a stub placed above the function under test reproduces
neither the bug nor the fix. **21 of the 26 fail against the parent commit**;
the 5 that pass in both are the unchanged-behaviour guards (a real
transcription, a genuinely empty one, and the two success paths).

Also closed a real leak found while writing those tests: urllib hands back an
`HTTPError` that *is* an open file-like object over a spooled temp file, so a
server 500ing on every utterance leaked one per utterance until the GC got to
it. potato had 183MB free the last time anyone measured. The witness is a
`ResourceWarning` assertion, not a comment.

## 2. Capture is blind while whisper runs — `106dcbc`

`transcribe()` is called from inside the capture loop. While it runs, the only
thing holding incoming audio is the kernel pipe behind `arecord`. Measured
here with a real pipe: **65536 bytes = 2.05 seconds** of 16kHz S16 mono,
against a remote transcription measured at 1–3s on this setup (FOCUS.md
2026-07-23 07:45). Past that, arecord's write blocks, its ALSA ring overruns,
and the audio is gone — with its `overrun!!!` complaints going to a temp file
this process only reads if capture *dies*.

Two halves, because the first alone makes things worse:

**The pipe is widened** to `CRT_CAPTURE_PIPE_BYTES` (256 KiB ≈ 8.2s), clamped
to `/proc/sys/fs/pipe-max-size` — asking for more is EPERM, which would lose
the widening entirely instead of taking what's available. The startup line now
prints the real depth in seconds, and warns outright if it is shallower than a
slow transcription.

**But a deeper pipe only trades dropped audio for stale audio.** Whatever
queued gets transcribed and answered later, while the room has moved on. So
after each transcription, anything older than `CRT_CAPTURE_BACKLOG_MAX_SECS`
(3s) is discarded — newest kept, since that is the half most likely to still
be someone talking — and the drop is announced on the pane, because silently
dropping audio is the whole failure mode here. `0` disables it. The drain runs
*between* utterances, never during one; that is the only moment it's safe, and
it's exactly where `transcribe()` already returns.

**The 3s default is not a by-ear number.** It has to exceed a healthy
transcription's stall so a working console never drops anything, and stay
short enough that the console never answers a question a whole conversational
turn late. 3s is the smallest value satisfying the first, which is decidable
from the measurements above. Both knobs are env-overridable if a live session
disagrees.

One supporting change: arecord's stdout is now unbuffered (`bufsize=0`), so
the kernel pipe is the *only* place queued audio lives. A `BufferedReader` in
front of it would hold bytes `FIONREAD` cannot see and the drain cannot
discard, making the backlog measurement quietly wrong by up to its buffer
size. `read_exact()` already looped over short reads; two new tests pin that,
including that a short read still reads as capture death.

**24 unit tests against real pipes with real `fcntl`/`ioctl`** — the capacity
numbers are measured, not asserted from a mock — plus an end-to-end run of the
real CLI against a fake arecord and a whisper that takes 5 seconds.
3 of the 24 pass at the parent commit: the two `read_exact` guards and the
measurement of the default pipe depth that motivates the change. The
end-to-end test fails at the parent on both new claims, while its "both
utterances still reached the log" guard passes in both — that guard is what
says the drain does not eat live speech.

## 3. Stress-test of what I touched

The failure modes this project actually has, checked against the diff rather
than against the suite being green:

- **A drain that blocks the loop** would be worse than the bug. It only ever
  reads bytes `FIONREAD` already said were queued, and it is the sole reader,
  so the count cannot shrink underneath it. Test: a drain on an idle pipe with
  no writer returns immediately.
- **A drain that desynchronises the reader.** Everything discarded is rounded
  down to a whole 100ms analysis chunk, so `read_exact()` stays frame-aligned.
  Asserted directly on the bytes left in the pipe.
- **A drain that runs mid-utterance** would excise the middle of a sentence —
  the `f13c7a4` bug from cycle three, reintroduced by a different route. It is
  called at one site, immediately after `transcribe()` returns, which is by
  construction between utterances.
- **Masking capture death.** A dead arecord leaves a short read at EOF; the
  drain consumes queued bytes but cannot consume the EOF, so the `exit 3` path
  from cycle one still fires. Pinned by a test.
- **Second-reader starvation** (this repo's oldest audio constraint):
  unchanged — still exactly one `arecord`, one reader.
- **Control-file race:** untouched; the drain reads no control state.
- **A deeper pipe on a 905MB Pi:** 256 KiB of pinned kernel pages, 0.03% of
  RAM.

## 5. New issues found this cycle

- **The follow-up problem had a second, physical cause the whole time.** Four
  cycles of work on that symptom — the sticky-conversation window, the arm
  window, the wake pool — all reasoned about the *gate*, which only decides
  what to do with audio that exists. Nobody asked whether the audio existed.
  Generalising: when a symptom survives repeated fixes at one layer, the next
  question is whether the layer below it ever ran, not whether the fix was
  right.
- **The invisible-evidence pattern, again.** arecord's overrun warnings were
  captured all along — into a temp file read only on capture death. Cycle four
  found the same shape in the test runner (a header printed for a test that
  did not exist); cycle six in `capture_pane()`. Evidence collected and never
  read is indistinguishable from evidence never collected.
- **`crt-stt-stream.py` carries a private copy of both defects, and nothing
  launches it.** Its own `transcribe_remote()`/`transcribe()` return `""` on
  error, and its callers do `transcribe(...).split()`, so it cannot inherit
  the `None` fix without changing them too. Left alone deliberately: patching
  code nothing runs, on a night when the same defect was live on the boot
  path, is the wrong order. Registered in `BATCH-NOTES.md` — the real question
  is whether it should exist at all.
- **A doc that names a missing file reads as current.** `STT-MECHANISM.md` —
  the file `CLAUDE.md` sends every fresh instance to — pointed at
  `bin/dexter-whisper-server.py` on "dexter's Ryzen host" and described the
  mic as `crtmic`, a dsnoop wrapper. Both are crt-vm-era. Same class as cycle
  five's topology correction; fixed in `81d78db`.
