## 1. A dropped tunnel looked exactly like a quiet Claude — `9eeccc3`

This is the failure mode FOCUS.md's *current top priority* names by name
("watch specifically for tunnel drops"), and it turned out to be invisible by
construction on both sides.

**potato's side.** `crt-secretary.py`'s `send_to_claude()` threw away its
result. On the remote path, `_bridge_request()` returns `""` for *any* socket
failure — tunnel down, bridge stopped, connection refused. So the send was a
silent no-op, and `handle()` went on to:

1. fire the `thinking` earcon — a promise to the user that an answer is coming,
2. sit through `wait_for_claude_reply()`, polling a socket that would never
   answer, until `CLAUDE_IDLE_SECS` expired,
3. and finish with `route_claude_reply("")` → *"I sent that to Claude but
   didn't catch a reply — check the screen."*

Nothing was sent. And the screen it points at is blank **precisely because**
the brain isn't there. A user following that instruction learns nothing, and
the actual cause — a dead reverse tunnel — is recorded nowhere at all.

**mandark's side was equally blind.** `crt-remote-claude-bridge.py`'s `SEND`
handler ran two `tmux send-keys` calls, ignored both return codes, and replied
`OK` regardless. A tmux session that had died or been renamed answered exactly
like a working one. It now checks both and replies `ERR <tmux's own reason>`.
The Enter is checked *separately* on purpose: the literal text can land and the
newline not, which leaves a half-typed prompt sitting in Claude's input and no
reply — the most confusing of the failure modes, and completely silent before.

**Safe in either deployment order**, which matters because the two halves live
on different machines and I can only deploy one of them:

| | old secretary | new secretary |
|---|---|---|
| **old bridge** | today's behaviour | detects the tunnel-down case (`""`); still trusts a stale `OK` |
| **new bridge** | ignores the response, unchanged | full detection |

`OK` is byte-identical for the working case, so nothing has to be restarted in
lockstep. The dominant failure — the tunnel itself dropping — is caught by the
potato half alone.

**What the console does now when an utterance doesn't land:** the `oops`
earcon, a spoken line deliberately worded to be distinguishable *by ear* from
the reached-Claude one ("I can't reach my brain right now, so that didn't go
anywhere"), the same line pushed to the `mono` window `handle()` just switched
to so the tube isn't blank, and an append to `~/.crt/brain-unreachable.log`
with the reason. `bin/crt-wake-router.py`'s `none` route already specified this
behaviour — *"the caller should give a short honest earcon/line … NOT
silence"* — it simply had no caller on this path until now.

**A quieter bug fell out of the same fix.** `_confirm_in_background()` —
STT-CONFIDENCE.md's background confirmation pass — recorded a Claude call and
then scored the resulting empty reply as a *mismatch*. So every utterance
spoken while the tunnel was down taught the confidence model that its own local
playbook disagreed with Claude, from an exchange that never happened. It now
returns before recording anything.

18 new tests. The ones that matter assert behaviour, not wording: `handle()`
must not wait on a send that never landed (the stub `fail()`s if it's called),
must not fire `thinking`, must not claim it sent anything, and must still fire
`thinking` on the success path.

## 2. A status command that could answer about the wrong port — `26cd8df`

`bin/crt-mandark.sh` is the tool Zach runs to answer "is the brain reachable".

## 1. Your reply, and the hole beside the fix — `b37bbad`

Your note quoted the "Observation, deliberately not changed" bullet about the
VAD checking `MUTED` only at utterance onset. That text lives in the preserved
*second*-cycle section of the report; the third cycle acted on it and landed
`f13c7a4`. So the first thing I did was check that fix is real rather than take
the report's word for it: `test_duck_midutterance_excision.sh` drives the real
CLI and still measures 300cs where the pre-fix code gave 400cs, and the
truncating alternative would give 110cs. It holds.

**What was still open is the same leak one buffer earlier.** The pre-roll deque
(`CRT_VAD_PREROLL`, 3 chunks) exists to prepend the moments *before* onset,
because a first word's attack sits under the VAD threshold. `pre.append(data)`
ran unconditionally — ducked or not. So:

| path | our own playback reaches whisper? |
|---|---|
| utterance *starts* during playback | no — start gate, always checked `MUTED` |
| duck arrives *mid*-utterance | no — since `f13c7a4` (freeze + excise) |
| playback sits in the pre-roll when the speaker starts | **yes, until this commit** |

Reachable on the live default path, in the flow the stability bar cares most
about: `addressed` (`CRT_EARCON_ON_ADDRESSED`, default **ON**) fires
immediately after `emit()` — exactly when a speaker carries on into a follow-up
utterance. At `CRT_VAD_PREROLL=3` the exposure is the ~100ms after the duck
lifts; the knob widens it linearly.

Witness: `tests/test_duck_preroll_leak.sh` drives the real CLI and measures the
**peak amplitude of the first 100ms of the WAV handed to whisper**, not its
duration — playback is emitted at 0.9 and speech at 0.3, so this is a 3x
separation rather than a chunk-counting argument that timing jitter could flip.
Against the parent commit it reports **29490**, which is exactly the playback
level; after the fix, **0**. The test raises `CRT_VAD_PREROLL` to 8 on purpose,
so the verdict does not hinge on winning a one-chunk race between the CTL line
and the audio it refers to.

The fix is `if not MUTED: pre.append(data)` — which splices the pre-roll across
the duck the same way `utt_chunk()` splices the utterance body. What leads the
utterance becomes the room tone from just before playback started.

`STT-MECHANISM.md` gained the matching paragraph: a follow-up in older
`stt.log` entries that picked up a phantom leading word now has a real
explanation that isn't "whisper misheard it".

**Stress-tested, one consequence worth knowing:** a *leaked* mute now also
freezes the pre-roll, so after `CRT_CTL_MUTE_MAX_SECS` (45s) force-clears one,
the next utterance gets a 300ms lead-in from 45s earlier. It's room tone, not
speech — ending an utterance needs 0.8s of trailing silence and the deque only
holds 0.3s, so it cannot be holding the tail of a word. Accepted.
