## 1. A contract the live path could not reach — `a9e899b`

`ArmState.arm()` in `bin/crt-wake-arm.py` says of itself:

> Always starts a FRESH session, including when one is already open — saying
> the wake word again is deliberate, so it resets the `ARM_MAX_SECS` ceiling
> rather than being swallowed by the conversation already in progress.

`tests/test_wake_arm.py` asserted that. It asserted it by calling `arm()`. In
`crt-stt-solo.py`'s `emit()`, an utterance arriving while armed runs the
consume-follow-up check first and **returns** as soon as it consumes — so
`arm()` was reachable only from a disarmed state, which is the one state where
resetting a ceiling means nothing.

`CRT_WAKE_ARM_ENABLED=1` is set in potato's `~/.bash_profile`, so this is the
live path. What it costs, in the vocabulary of the report that created this
feature: someone re-says the wake word out of habit — which is exactly what the
2026-07-23 log shows people doing — and still hits the 60s ceiling measured from
their **first** wake. The utterance after that is gate-dropped in silence,
seconds after they addressed the console by name. That is the same complaint the
arm window exists to fix, one minute later instead of one utterance later.

`consume_arm_with_followup()` now takes the follow-up's own wake classification
and re-arms instead of sliding when it carries one. A plain follow-up still
slides *inside* the ceiling, so ambient chatter still cannot ratchet the mic
open; only a word someone actually said can. `classify_wake_match()` is computed
at most once per utterance either way — the arm call below reuses it rather than
paying a second `os.stat` of `stt-fixups.json`.

**7 tests** (`tests/test_wake_rearm_ceiling.py`). Three drive the real `emit()`
with the real gate, faking only the sinks and the arm module's clock. The
load-bearing one fails against the parent as `'and wednesday' not found` — an
utterance spoken eight seconds after the wake word, never delivered — rather
than as a missing-kwarg error. `test_wake_arm.py`'s own version now points here.

## 2. A book you could only ever answer once — `bb2bd8e`

The Book Game funnel is idle-bait → scan → question → **spoken answer** → STT
training log, and its premise is a shelf someone picks up again and again.

`register_book()` caches on purpose: a re-scan returns the existing row
untouched, keeping the question, the quote and the LCC computed once. But
`first_scanned` was the only time the `books` table carried, so a re-scan left no
record anywhere that a scan had happened — and `crt-book-answer-listen.py`
derives "a question is pending" entirely from a timestamp.

So the last link of the funnel worked exactly once per book. Scan a book already
on the shelf: `crt-book-console.py` renders its question on the tube exactly as
for a new one, the person answers aloud, and nothing grades it, nothing is
logged, nothing is announced. **This is FOCUS.md's fourth stability-bar item
failing on the second scan of anything.**

The second mode is worse than silence. With another book registered inside
`CRT_BOOK_ANSWER_WINDOW_SECS`, the answer to the re-scanned book was graded
against **that** book's question — a training row whose `expected` belongs to a
different book, written into the file this console exists to fill, and announced
on the tube as *"nope, it was 1815"* for a question nobody was asked.

Scanning is the event; registering is a side effect of the first one.
`touch_scan()` separates them, stamping a new `last_scanned` column at both scan
sites — `handle_scan` (the `book` window) and `crt-book-game.py`'s own CLI.
`get_pending_question` orders by `COALESCE(last_scanned, first_scanned)`:
potato's existing `books.db` has that column NULL everywhere, so those rows keep
behaving exactly as they do today. No backfill, no migration to get wrong.

**10 tests** (`tests/test_book_rescan_pending.py`). Three drive the real
`handle_scan`; against the parent they fail with what someone at the console
would get, including the corrupted row, which fails as `'1815' != 'fiction'`.

## 3. Two writers, one temp file — `0eb2d38`

`stt-fixups.json` is what this console has learned about how this room says its
wake word. Two writers, one live reader:

| | |
|---|---|
| `crt-calibration-game.py` | a human confirming a mishear by ear |
| `crt-stt-training-merge.py` | the `stttrain` window, unattended, every 600s |
| `crt-stt-solo.py` | the wake gate, re-reading every utterance since `0ccdf13` |

Since `24a94ac` the two writers agree on which file that is. Both did
read-modify-write-whole-file through a temp path named `<file>.tmp`. **The same
one.**

- **Lost update.** Each computes its new dict from a snapshot read moments
  earlier and writes the whole file, so the later write silently drops whatever
  the earlier one added. What the calibration game adds is a human-confirmed
  wake-word alias — its own docstring calls those the strongest evidence this
  project collects, and they cannot be re-derived, only re-earned by someone
  standing at the mic saying a word until it is misheard the same way twice.
- **Torn file.** `open(tmp, "w")` truncates. A merge tick landing inside a
  calibration save truncates that save's half-finished temp, and whichever
  `os.replace` runs puts the wreckage where the real file was. `os.replace`
  protects the *reader* from a half-written file; it does nothing to protect two
  writers from each other.

Cycle 11 filed this and deferred it as interacting with question 4 — whether
unattended merges should reach the gate at all. It does not: whatever the merge
is *allowed* to write, it must not be able to write half of it.

`bin/crt_fixups_store.py`'s `update(path, mutate)` does the read, the mutate and
the rename inside one `flock`, and the temp path carries the pid. Readers need
nothing from it — `os.replace` is atomic, which is why `crt-stt-solo.py`'s
`FixupsFile` is untouched. The lock is a **sidecar** rather than the file itself,
because the file gets replaced by rename and a lock on the old inode means
nothing to whoever opened the new one. A directory where the lock file cannot be
created degrades to unlocked — the behaviour both writers already had — rather
than refusing to save a human's confirmation.

**Retires `save_fixups(data, path)`.** Taking a whole dict from a caller holding
a snapshot is the API that made the lost update possible;
`save_fixup(fragment, target, similarity, path)` adds the one entry inside the
lock. The two writers had also drifted to different indents (2 and 4), so a
human confirming a single word reflowed the entire git-tracked file and buried
their one real change in the diff. One `dumps()`, matching what
`bin/stt-fixups.json` is actually committed as.

**13 tests.** `tests/test_fixups_two_writers.py` deliberately does *not* import
the new module, so it runs against the parent too — all three fail there, the
headline one as `'slide' not found`, a human's confirmation erased by a merge
tick. `tests/test_fixups_store.py` adds ten more, including three real processes
hammering one file while a reader polls for a torn parse.
