## 1. A loop that ended on one bad row — `442562b`

`crt-console.sh` starts eight long-lived Python windows and wraps each in
`; exec bash`. Four ran their whole loop with no guard on the body:

| window | script | what a single raise costs |
|---|---|---|
| `book` | `crt-book-console.py` | the window the console **boots selected** — its pane is the tube |
| `bookidle` | `crt-book-idle-bait.py` | step one of the funnel: no bait, no scan |
| `bookanswer` | `crt-book-answer-listen.py` | the last link: the spoken answer, the training row |
| `stttrain` | `crt-stt-training-merge.py --loop` | unattended STT learning, for the rest of uptime |

The raises are ordinary: a locked `books.db`, a malformed `questions_json`,
ENOSPC on a Pi's SD card mid-write, `os.path.exists(stt.log)` followed by
`os.path.getmtime` of a file removed in between. And behind `; exec bash` the
window does not even close — you get a shell prompt, and nothing anywhere says
so. Three of those four are steps in the Book Game funnel, which is an **unmet
item on FOCUS.md's own stability bar**.

Cycles 9 and 10 each filed this and each deferred it to "the supervisor
question." Splitting that question gives two different jobs, and only one of
them needs a supervisor:

- **transient, per-iteration** — skip that iteration, say so, keep going. Needs
  nothing but the process itself. That is this commit.
- **the process is gone** — only something outside it can notice. Still ranked
  item 8, still `[hw]`.

`bin/crt_loop_guard.py` is a context manager around one iteration. Reporting
follows what the rest of `bin/` settled on: **once per distinct cause** (window 1
fades the person's own words off the top, so a repeating fault must not own the
screen), plus a **recovery line naming how many were swallowed**, so nothing it
suppresses is left without a trace.

What it deliberately does *not* do, each tested:

- **It does not sleep.** Pacing stays where the caller can see it; a hidden
  backoff would make a hot loop look healthy. All four callers already pace
  themselves.
- **It does not catch `BaseException`** — Ctrl-C and a deliberate stop still
  stop, the distinction `2a346ae` drew for `crt-stt-solo.py`.
- **`--loop` and one-shot want opposite things**, and both had the one-shot's.
  `crt-stt-training-merge.py --loop` now survives; a one-shot run still exits
  non-zero rather than being an exit-0 no-op.
- **Tracebacks are off by default, and `book` passes `echo=False`.** That pane
  is the tube, and `draw()` homes-and-clears — a report printed into the frame
  would sit there until the next scan, which after the idle screen is up may be
  a long time. It still reaches window 1.

Also closes a comment that outlived its implementation: `tail_new_lines`'
docstring in `crt-book-console.py` points at *"main()'s crash-log wrapper below"*
for the traceback-scrolls-off-a-15-row-pane problem. There was no such wrapper.

**25 tests** (`tests/test_loop_guard.py`). The four call-site tests drive each
script's real `main()` with one inner function poisoned, and reach the guard
through `CRT_THOUGHT_LOG` rather than by touching the module — so against the
parent they fail with the actual defect (the exception escaping `main()`), not
with "no attribute loop_guard". Each stops via a `KeyboardInterrupt` raised by
the fake clock or tail, which doubles as the proof that a real Ctrl-C still gets
out: if the guard swallowed it, those tests would hang rather than pass.

## 2. The wake gate and its two writers, pointed at one file — `24a94ac`

`bin/stt-fixups.json` is what this console has learned about how this room says
its wake word. Three scripts touch it. They did not agree on the env var that
moves it:

```
crt-stt-solo.py            CRT_STT_FIXUPS        reader -- the wake gate
crt-calibration-game.py    CRT_STT_FIXUPS        writer -- a human's ear
crt-stt-training-merge.py  CRT_STT_FIXUPS_PATH   writer -- unattended
```

They agree on the default, so nothing is broken with neither set — which is why
this has sat there for as long as both files have existed. Set one alone and a
writer and the reader are pointed at different files, with no error anywhere:
the calibration game prints `Saved`, the merge loop prints `auto-merged`, and
the word still does not wake it. That is the same silent shape `0ccdf13` fixed
one layer up last cycle. The reason to set it at all would be a live debugging
session, which is exactly when a split like this costs the most.

`bin/crt_config.py` resolves it once, honouring both spellings, canonical first.
`CRT_STT_FIXUPS` is canonical (two of the three, plus
`tests/test_fixups_reload.py`). `CRT_STT_FIXUPS_PATH` is **kept working rather
than retired** — retiring it would break any live shell or tmux env on potato
that already sets it, and this tier cannot see potato to check. A genuine
disagreement between the two is reported rather than silently resolved, and the
resolver cannot raise: `crt-stt-solo.py` calls it at import, and a config-shaped
complaint must never be why the STT engine fails to start.

That file is also the landing spot ranked item 1 asks for, opened with the
instance actually found rather than left as a plan. **The port and the ALSA
device are not moved into it here** — both have live-behaviour questions still
staged for you (question 12 below).

**11 tests** (`tests/test_config_fixups_path.py`); three load all three real
scripts and assert their resolved `FIXUPS_PATH` is the same string, and each
fails against the parent. One of those failures is a second latent bug the
parent shares: with either var set to the empty string,
`os.environ.get(name, default)` returns `""` rather than the default, so the
path became `""`.

## 3. Window 1 would have died on one byte — `ae54ef4`

Found while re-reading §1. Every one of those reports goes to
`~/.crt/thoughts.log` for `crt-monologue.py` to render, and that reader does

```python
with open(LOG) as f:          # strict UTF-8
```

inside a loop that catches `OSError`. `UnicodeDecodeError` is a **ValueError**.
A reader that catches up to a writer mid-flush sees a partial UTF-8 sequence —
book titles carry accents, idle-bait quotes carry em-dashes — and window 1 goes
dark. So does `crt-claude-bridge.py`, which feeds it, reading a transcript file
Claude Code is actively appending to.

Worse for §1: `crt-book-console.py`'s and `crt-book-answer-listen.py`'s tail
generators raise it from inside the `for` **iterator**, which is outside the
LoopGuard — that guards the body, deliberately and documentedly. So this was one
of the few remaining ways those two windows could still die outright, and a
barcode scanner is a keyboard-emulating device that can put arbitrary bytes into
`scanner.log`.

`errors="replace"` in all five reads. A replacement character in one line is a
much smaller loss than the window that was rendering it. The one-shot readers
(`crt-book-game-stats.py`, `crt-pager.py`, `crt-predict.py`) are deliberately
left strict — those exit loudly and immediately, which is right for a tool
someone just ran by hand.

**5 tests**, all five failing against the parent. Two run the real
`crt-monologue.py` and `crt-claude-bridge.py` as child processes: their reads
live inside never-returning `while` loops, so the only alternative was asserting
on the source string, which is the "grep proves it" shape `ad41f5a` called out.

## 5. New issues found

- **`crt-stt-training-merge.py` writes `fixups_path + ".tmp"`.** Two instances —
  a stray one-shot run while `stttrain` is looping — would race on the same temp
  name, and either could `os.replace` a half-written file into place. The atomic
  rename protects the *reader*; it does not protect two writers from each other.
  Not fixed tonight: the fix is a per-process temp name, and it interacts with
  question 4 about whether unattended merges should reach the gate at all.
- **A `LoopGuard` cannot tell a hiccup from a permanent fault.** It reports the
  first occurrence of each distinct cause and keeps going. That is deliberate
  (question 1), but it means a window can now be *up and useless* where before
  it was down. Up-and-complaining is better than a bash prompt, and window 1
  says which window and why — it is still worth knowing the mode exists.
- **The two new modules are loaded by path, so each script parses its own
  copy.** `spec_from_file_location` does not share across loaders. Negligible at
  ~60 lines each; noted only so it is not a surprise if the pattern spreads.
