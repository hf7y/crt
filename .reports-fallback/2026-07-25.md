## 1. Born believing it has 80 columns — `b019c90`

`crt-console.sh` builds every window with `tmux new-window -d` and runs
`exec tmux attach` only at the very end, after all of them exist. A detached
tmux session is 80x24 whatever the tube is. Measured, not assumed:

```
$ tmux new-session -d -s t; tmux new-window -d -t t "python3 -c 'shutil.get_terminal_size()'"
os.terminal_size(columns=80, lines=24)          # tmux 3.6
```

`crt-book-console.py` called `bg.detect_screen_size()` once, on the first
line of `main()`, and never again. So every screen it paints — the shelf,
the question, the graded answer, a failed lookup — is laid out for a screen
twice as wide and nine rows taller than the one it is on. Each line wraps to
two rows; 24 lines become 48 in a 15-row pane; the question scrolls its own
top away before anyone reads it.

Here is the same question as it was being laid out, rendered from the real
function — 80 columns of it, going into 40:

```
|                          Nineteen Eighty-Four (PR6029                          |
|                                                                                |
|                            Was Nineteen Eighty-Four                            |
|                           published before or after                            |
|                                     1950?                                      |
|                                                                                |
|                                 before / after                                 |
```

and as it is drawn now, after all three commits:

```
|      Nineteen Eighty-F.. (PR6029)      |
|                                        |
|        Was Nineteen Eighty-Four        |
|       published before or after        |
|                 1950?                  |
|                                        |
|             before / after             |
```

**This is the third window with this exact bug and the last one that still
had it.** `crt-screensaver.py` was fixed on 2026-07-23 — its own comment
says why, in the same words — and `crt-monologue.py` in `6aecc39` last
night. Both times the window that draws the question was left holding it.

**Two halves.** `detect_screen_size()` now honors `CRT_COLS`/`CRT_ROWS`, the
pins `crt-console.sh` already writes and the other two renderers already
read; a pin that fixes two of the three and is silently inert in the third
is this project's signature bug (`CRT_CTL_FILE`, `CRT_IDLE_FACE_WINDOW`), not
a gap worth leaving. And the console re-measures every tick, repainting the
screen currently on the tube when the answer changes.

Repainting on the *change*, not merely at the next draw, is the part that
matters: there may not be a next draw. In the historical layout `book` is
the boot-default window and its idle shelf screen is what the tube holds
until somebody scans something.

**Tests: 7 in `tests/test_book_console_size.py`, 4 fail against the parent.**
The load-bearing ones run the real console on a real pty and resize it with
a real `TIOCSWINSZ` — which is exactly what an attaching tmux client does to
these panes — then assert a frame comes back at the new width. Not a
monkeypatched seam: the claim is about a `main()` that read the number once,
and a helper returning the right value proves nothing about that.

## 2. The question survives its own resize — `16f40c9`

A resize while a question is up has to correct *that* screen. Since `967af9c`
it holds the entire tube for `CRT_BOOK_CONSOLE_IDLE_SECS`, so it is what
someone is looking at when the client attaches.

Each repaint binds what it draws at the draw site rather than reading the
console's live state, so the reverse is also true: a resize cannot resurrect
a question that has since timed out, or an answer belonging to a different
book. Third pty case scans, watches the question land at 80 columns, resizes,
and asserts the same book and its options come back inside 40.

## 3. A dangling paren, found by looking at the screen — `fbe2cea`

Visible in §1's first block, and the reason to render things rather than
reason about them: `Nineteen Eighty-Four (PR6029`. The title and the LCC call
number were composed into one string and *then* cut to the 28-character title
budget, so the closing paren was simply the character that fell off. On a
40-column tube a half-open parenthetical reads as a broken render, not as a
long title.

Composed against the budget instead. `bg.title_budget()` exposes the number
`render_question_screen()` truncates against — it now calls it, so the two
cannot drift — and `bg.elide()` cuts with a visible `..` so a shortened line
says so. What survives when something must give is the **call number**: you
are holding the book, so its name is the part you already know, and
BOOK-GAME.md's resolved v1 decision made this screen the only place the LCC
appears at all. Below 8 characters of remaining title that stops paying and
the call number goes instead. That direction is a judgement call — question 3
below if you disagree.

## 4. Stress-test of what I touched

Against this project's actual failure modes, not against it parsing:

- **Cost per tick.** One `ioctl` at `POLL_SECS` (0.5s), or two env reads and
  no syscall at all once `CRT_COLS`/`CRT_ROWS` are pinned. Nothing on a Pi 3B+.
- **Flapping.** `os.get_terminal_size` on a pty is stable, and with stdout
  redirected the fallback is constant. Only a real client resize changes the
  answer, so the repaint cannot chatter.
- **A raise inside the repaint.** The size check sits inside the loop body's
  `LoopGuard("book")`, so a sqlite hiccup in `book_count()` during a repaint
  is reported on window 1 once per cause and the window keeps working —
  rather than the resize being the thing that finally kills it.
- **Ordering against a scan.** The check runs at the end of the tick, after
  `show_scan`. A scan and a resize in the same tick end with the question at
  the new size, not with the idle screen over the top of it.
- **Live behaviour, unchanged today.** Nothing in the repo exports
  `CRT_COLS`/`CRT_ROWS` into the book window — `crt-console.sh` sets them as a
  command prefix on the screensaver's launch line only, which does not leak.
  So on potato the only change is the re-measure. Verified by grep, not
  assumed.
- **A typo'd pin.** `_env_dim()` is junk-tolerant. The old bare `int()` would
  have raised `ValueError` out of `main()`'s first line and left a bash prompt
  where the console's face goes — the failure this window has been taught to
  avoid everywhere else.
- **A dead pty.** `draw()`'s `OSError` after `tmux kill-window` is caught by
  the guard, reported once, and the loop continues. Pre-existing, unchanged,
  noted so it is not read as new.
