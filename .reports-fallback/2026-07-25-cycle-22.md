## 1. A warning that couldn't see the case it was for — `36f6457`

FOCUS.md bar item 3 is "capture device resolved by NAME — **code done** …
never run against potato's real `arecord -l` output". I can't run it against
potato. I can run it against the listing shapes potato produces, and the
resolver has two defects.

The resolver has three outcomes — matched a card name, matched nothing but
guessed, found no cards at all — and returned only the device. So the caller
re-derived which had happened, by testing whether `CRT_AUDIO_DEV_NAME` appeared
anywhere in the raw `arecord -l` text. That is a different question:

```
card 1: Device [USB PnP Sound Device], device 0: USB Audio [USB Audio]
                ^ the name that must match      ^ but this matched instead
```

`USB Audio` is the **device description** of essentially every USB audio-class
adapter, not just of a card whose **name** matches. So the substring test passed
while no card name had. Measured against the parent, with two capture cards
present:

```
resolved: plughw:0,0        <- the onboard analog input, not the USB mic
warning would fire? False
stderr -> ''
```

It picks whichever card is listed first and says nothing at all. The one case
the warning existed for was the one case it could not see.

The resolver now reports how it resolved, and `capture_device_warning()` turns
that into the message — naming every card it *did* see, so a miss can be acted
on without rerunning `arecord` by hand on a box you may not be sitting at. The
message is a pure function of the outcome and is tested directly, same shape as
`capture_death_report()` already in that file.

**The bash port had the other half.** `crt-lib-audio-device.sh` is the twin used
by `crt-audio-doctor.sh` and `crt-capture-watchdog.sh`. On a name miss it fell
back to `plughw:0,0` — while its Python original deliberately does not, and
documents why in its own docstring: on potato card 0 is the onboard
playback-only card, **absent from a CAPTURE listing entirely**, where `arecord`
exits instantly having produced nothing. Same input, two answers:

```
shell : plughw:0,0
python: plughw:2,0
```

For the watchdog that closes a loop: `arecord -D plughw:0,0` ends immediately →
`peak_stream` ends → *"reader ended/timed out -- treating as stale"* →
`recover()`, which runs `pkill -f 'arecord .*(plughw|crtmic|hw:)'` — **killing
the console's actual capture** — then does it again every `CRT_WD_COOLDOWN`
(15s), forever, logging a wrong diagnosis each time. The watchdog is opt-in and
not wired into `crt-console.sh`, so this is "when you run it", not "on every
boot". It now guesses the first *listed* card, same as Python, and warns on
stderr, which every caller here leaves alone because they all read stdout with
`$(...)`.

`tests/test_audio_device_lib.sh`'s own case — *"no matching card falls back to
plughw:0,0"* — was pinning that divergence in place, while
`test_capture_device.py` asserted the opposite for the same scenario.

## 2. The suite writes to the live console's mute channel — `39ba627`

Found while checking my own work was clean. It isn't mine: reproduced against a
fresh clone of the parent commit. Five test files write into the real `~/.crt`.

Not their own scratch files — each of the five carefully makes a tmpdir for
those. It's the **module-level defaults** of the `bin/` code they import:

| file | what reads it |
|---|---|
| `~/.crt/ctl` | the capture-duck control channel a **running** `crt-stt-solo.py` reads live |
| `~/.crt/claude-window-active.state` | what `crt-window-switcher.py` reads to decide a brain is behind the screen |
| `~/.crt/thoughts.log` | window 1 |

On potato that means running the suite appends a few hundred `mute 1`/`mute 0`
pairs to the live control file — the file on this box is already hundreds deep —
and stamps the switcher's state with *now*, holding window 1 for the next 30
seconds. The engine's startup CTL replay already ignores a stale momentary
`mute`, so a cold boot was safe; **a console that was already up was not.**

Pinned in `run_tests.sh` for the whole suite — cycle 21's own lesson after this
class recurred within one cycle, *pin the default, not each path* — and in each
of the five, for a standalone `python3 tests/test_secretary.py`. All five
verified clean standalone, and still passing.

Pinning only covers the vars known today, and this is the third cycle to find
this class, so the runner now snapshots `~/.crt` and **fails naming whatever
moved**. It earned that on its first run: two env vars name `thoughts.log`
(`CRT_THOUGHT_LOG`, and `CRT_STT_GATE_LOG` via the gate-drop path), so pinning
the obvious one left the channel open. A third writer, `crt-bell-test.sh`,
hardcodes the path with no variable at all — nothing in the suite runs it, so
it's noted, not fixed. **That's question 2 below.**

## 3. The guard's own silent-pass — `31f997a`

The guard skips when a console is running on the same box, since then `~/.crt`
moves for real reasons and nothing could attribute them. It detected that with
`pgrep -f 'crt-stt-solo.py'`, which matches any command line that merely
*mentions* the script — a grep, an editor, the shell that launched the suite. I
hit it immediately: my own probe command matched itself.

A skip is not a pass, but a skip that fires by accident and says nothing is the
same class the guard exists to catch. It now names the PID and how to check it
(`ps -p <pid> -o args=`), and takes an explicit
`CRT_TEST_SKIP_LIVE_STATE_GUARD=1`. Both paths exercised, plus the failure path
against a deliberately polluted sandbox dir.

## 4. Stress-test of what I touched

Against this project's actual failure modes, not against it parsing:

- **The new tests fail against the parent**, verified by stashing the fix rather

  `arecord` subprocess is untouched.
- **The explicit override still wins outright.** `CRT_AUDIO_DEV` short-circuits
  before any parsing — the "never remove the manual escape hatch" posture from
  FOCUS.md's 07:20 note. Still covered by its own test.
- **One behaviour change I'd flag:** `CRT_AUDIO_DEV_NAME=` (explicitly empty)
  used to match the first card silently; it now returns the same device but
  calls it a guess and warns. There is no name to match, so calling it a match

- **`~/.crt` verified byte-identical** before and after every full suite run,
  by a check independent of the new guard.
